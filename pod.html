1. Simple Explanation

The Shared Apartment Analogy

Think of a Pod like a shared apartment on a Linux machine, and containers inside it like roommates living in that apartment:

  • Each roommate (container) has their own bedroom: their own root filesystem and application process.
  • All roommates share the same apartment address, Wi-Fi router, and kitchen/storage closet: the Pod's IP address, localhost, ports, and mounted emptyDir volumes.
  • If the apartment gets evicted/rebuilt (the Pod is rescheduled): all roommates move together—and they get a new apartment address (new Pod IP).

In Kubernetes, a Pod is the smallest deployable unit you create and manage—not a single container.

2. Deep Technical Explanation

Kubernetes does not run "Pods" directly as a Linux kernel object. Instead, a Pod is a co-location and shared-context specification orchestrated by kubelet and the CRI runtime (containerd / CRI-O + runc or crun) on a worker node.

When you create a Pod with one or more containers:

  1. Shared Network Namespace (net): All containers in the Pod join the same network namespace. They share one IP address, one routing table, one iptables/nftables view, and the same lo (127.0.0.1) loopback interface. Container A can reach Container B on localhost:<port>.
  2. Shared IPC Namespace (ipc) (by default in standard specs): Containers can use System V IPC or POSIX message queues/shared memory with each other.
  3. Optional Shared PID Namespace (pid) (when shareProcessNamespace: true): Containers see each other's processes (ps aux) and can signal them—though note that even then, each container process typically has its own sub-reaper or relies on a pause/init process rather than acting as true PID 1 for the whole host.
  4. Separate Mount (mnt) & UTS Namespaces: Each container normally gets its own root filesystem (overlayfs) and hostname/UTS context unless configured otherwise.
  5. Shared Volumes: Volumes declared at the Pod level (like emptyDir or ConfigMap mounts) are mounted into specified paths inside each container's mount namespace.
  6. Shared Cgroup Resource Accounting: Both per-container cgroups (for individual container CPU/memory limits) and a parent Pod cgroup (for Pod-level QoS and eviction accounting) exist under the cgroup hierarchy (systemd or cgroupfs driver).

3. Internal Working & Kernel Perspective

At the Linux kernel level, there is no pod syscall or pod struct. A Pod is built out of Linux namespaces (clone(2) / unshare(2) / setns(2)) and cgroups (cgroup2 filesystem):

Userspace

kubelet watches kube-apiserver, calls CRI (RunPodSandbox, CreateContainer, StartContainer), and runc sets up namespaces, mounts, capabilities, seccomp, and cgroups.

Kernelspace

The Linux kernel enforces namespace isolation (nsproxy), cgroup resource limits/accounting (memory and cpu controllers), network routing (sk_buff, veth, bridges/CNI), and filesystem access (overlayfs, vfs).

The "Pause" (Infra) Container

  • When CRI runs RunPodSandbox, the runtime starts a tiny infra / pause container first.
  • Its primary job is to hold open the Pod's namespaces (especially the network namespace) for the entire lifetime of the Pod. Even if an app container crashes and restarts, the Pod's network namespace stays alive via the pause container so the Pod keeps its IP address and localhost stays intact.

Key Syscalls & Lifecycles

  • Sandbox & Container creation: clone() / unshare() to create namespaces, setns() to join existing namespaces (e.g., app containers joining the pause container's network namespace), mount() / pivot_root() for rootfs and volumes, and writing PIDs to /sys/fs/cgroup/.../cgroup.procs.
  • Process lifecycle: Inside a container, the entrypoint process is PID 1 within that container's PID namespace. If it doesn't reap zombie children or forward signals properly, zombie processes can accumulate or SIGTERM can be ignored until SIGKILL (kill -9) after terminationGracePeriodSeconds.
  • Memory & Filesystem interactions: Memory usage includes page cache + anon pages (RSS / working set). Writing to a container's writable overlayfs layer hits copy-up overhead; emptyDir backed by disk uses node storage/tmpfs (if medium: Memory, it consumes RAM/page cache counted against memory limits).

4. Architecture & Flow

Here is how a Pod comes to life from manifest to running Linux processes:

  1. Manifest submitted (kubectl apply -f pod.yaml) → hits kube-apiserver → validated & persisted in etcd.
  2. kube-scheduler sees an unscheduled Pod (spec.nodeName is empty) → scores nodes (resources, taints/tolerations, affinity) → binds Pod to a worker node.
  3. kubelet on that worker node notices a Pod assigned to its node → calls CRI RunPodSandbox:
    • Creates cgroups for the Pod/sandbox.
    • Starts the pause container and creates the Pod's network namespace.
    • CNI plugin is invoked to wire the Pod's network namespace (typically a veth pair into a bridge/router/eBPF datapath) and assign the Pod IP.
  4. kubelet runs init containers sequentially (each must exit 0 before the next starts).
  5. kubelet starts main app containers (and sidecars), attaching them to the shared network namespace and mounting Pod volumes, then runs startupProbe, readinessProbe, and livenessProbe.

5. Real-World Production Examples

Sidecar Log Shipper / Proxy

Main app container writes logs to a shared emptyDir volume (or stdout); a sidecar container tails those files and ships them to Loki/Elasticsearch, or a service mesh proxy container intercepts local traffic.

Init Container Pre-flight Check

An init container waits for a database/migration job or downloads config/certs into a shared volume before the main web app starts.

Ephemeral Scratch Space

A video/image processing Pod uses an emptyDir volume for temporary chunks so files don't clutter the container's overlayfs upper layer.

6. Command Examples

A. Inspecting a Pod and its Node/IP/Containers

bash 
kubectl get pod web-api -n prod -o wide
  • Flags: -n prod specifies the namespace; -o wide adds Node name, Pod IP, and Nominated Node/Readiness gates to the output.
  • Output columns: NAME (Pod name), READY (ready containers / total containers, e.g., 1/1), STATUS (Running, Pending, CrashLoopBackOff, etc.), RESTARTS (container restart count), AGE, IP (Pod IP), NODE (scheduled worker node).
  • Internally: kubectl sends an authenticated GET request to kube-apiserver (/api/v1/namespaces/prod/pods/web-api), which reads the latest object state from etcd.

B. Deep-Diving Events, Conditions, and State Reasons

bash 
kubectl describe pod web-api -n prod
  • Internally: Queries kube-apiserver and formats Pod spec, status conditions (PodScheduled, Initialized, ContainersReady, Ready), volume mounts, QoS class, and recent Kubernetes Event objects—critical for seeing scheduling failures, image pull errors, or OOM/liveness kills.

C. Executing Inside a Specific Container & Checking Network/Processes

bash 
kubectl exec -it web-api -c app -n prod -- sh -c "ip addr && ps aux"
  • Flags: -i (--stdin) keeps STDIN open; -t (--tty) allocates a pseudo-TTY; -c app targets the app container (required when the Pod has multiple containers).
  • Internally: kubectl talks to kube-apiserver, which proxies/streams via SPDY or WebSockets to the kubelet on the node, which invokes the CRI runtime (containerd / runc) to exec a new process inside that container's namespaces.

7. Common Debugging Scenarios

  • Pod stuck in Pending: Usually FailedScheduling in kubectl describe—insufficient CPU/memory on nodes, unmatching nodeSelector/affinity, taints without tolerations, or unbound PVC.
  • Pod Running (0/1 Ready) but traffic isn't hitting it: readinessProbe is failing (app still warming up, DB connection down, or wrong probe path/port). kube-proxy/Service endpoints exclude unready Pods.
  • Pod restarting with OOMKilled (Exit Code 137): Container exceeded its memory cgroup limit (or node suffered memory pressure eviction). Note: 137 = 128 + 9 (SIGKILL).
  • Pod in CrashLoopBackOff: Container starts, exits non-zero (e.g., bad env var, missing config, unhandled exception), and kubelet backs off restarts exponentially (10s, 20s, 40s... capped at 5m).
  • Container A can't reach Container B on localhost: Verify both are actually in the same Pod (not two separate Pods/Deployments) and check which port Container B binds to (0.0.0.0 vs 127.0.0.1 inside the shared netns).

8. Interview-Focused Explanation

When asked: "What is a Pod and why doesn't Kubernetes just schedule single containers?"

  1. Atomic scheduling & co-location unit: A Pod groups tightly coupled containers that must be scheduled onto the same node, share lifecycle, and communicate/share data locally with low latency.
  2. Shared Linux namespaces & volumes: Containers in a Pod share a network namespace (one IP, localhost communication, shared port space—watch out for port collisions!) and can share volumes, while keeping isolated root filesystems.
  3. Ephemeral by design: Pods are mortal—they don't "self-heal" in place across nodes; controllers (like Deployment / ReplicaSet) replace unhealthy or evicted Pods with new ones that get new IPs.

9. Common Misconceptions

Myth "One Pod = One Container."

Fact A Pod can run multiple tightly coupled containers (main app + sidecar/adapter), plus init containers.

Myth "A Pod is a Virtual Machine."

Fact Containers in a Pod share the host Linux kernel; isolation comes from namespaces, cgroups, capabilities, seccomp, and MAC (like SELinux/AppArmor), not a hypervisor per Pod.

Myth "If a Pod dies and comes back, it keeps its IP and local disk writes."

Fact A recreated Pod gets a new IP and loses emptyDir / container writable layer data. Persistent data needs a PersistentVolume (PV/PVC), and stable network identity needs a Headless Service / StatefulSet pattern.

Myth "Liveness probe failure and Readiness probe failure do the same thing."

Fact Failed readinessProbe removes the Pod from Service endpoints (stops sending traffic); failed livenessProbe tells kubelet to kill and restart the container.

10. Advanced Concepts Related to Pods

  • QoS Classes (Guaranteed, Burstable, BestEffort): Determined by CPU/memory requests and limits on containers—directly affects which Pods get evicted first under node memory/disk pressure.
  • Ephemeral Containers (kubectl debug): Temporary containers injected into a running Pod's namespaces (useful for distroless/minimal images that lack sh, curl, or debugging tools).
  • Pod Overhead & RuntimeClasses: Accounting for extra resources used by the runtime/sandbox itself (especially relevant for sandboxed runtimes like Kata Containers or gVisor).
  • Graceful Termination Flow: Setting PreStop hook → sending SIGTERM to container PID 1 → waiting terminationGracePeriodSeconds (default 30s) while removing endpoints → sending SIGKILL if still alive.

Your Turn: Interview & Production Check

Answer these in your own words—don't look anything up, and explain the why behind your answers:

1. Beginner: Why do containers inside the same Pod share an IP address and can talk over localhost, while two different Pods cannot talk over localhost to each other?
Containers in the same Pod join the exact same Linux network namespace (netns) held open by the pause container, sharing one lo (127.0.0.1) interface and one Pod IP. Two separate Pods each have their own distinct netns and separate loopback interfaces.
2. Intermediate: Explain the difference between livenessProbe, readinessProbe, and startupProbe—and give a case where a misconfigured livenessProbe actually causes an outage.
startupProbe protects slow-starting containers before liveness/readiness take over; readinessProbe gates whether Service endpoints route traffic to the Pod; livenessProbe restarts a stuck/deadlocked container. Outage case: Making livenessProbe check an external dependency (like a shared DB)—a brief DB blip makes K8s restart every healthy app Pod simultaneously, causing a cascading outage.
3. Advanced: A container in a Pod is killed with exit code 137. Walk through what happens at the cgroup/kernel level and how you distinguish a container memory limit OOM vs. node-wide memory pressure.
137 = 128 + 9 (SIGKILL). When RSS + non-reclaimable page cache reaches the container cgroup's memory.max, the kernel cgroup OOM killer sends SIGKILL to a process in that cgroup (Reason: OOMKilled in kubectl describe pod, incrementing oom_kill in memory.events). Under node-wide memory pressure, kubelet eviction manager evicts Pods based on QoS class (Status: Evicted, reason Evicted / low node memory) rather than a container cgroup OOM kill.
4. Scenario-based Production: You deploy a Pod with an app container and a log-forwarder sidecar sharing an emptyDir volume. The app container crashes and restarts 3 times. What happens to: (a) the Pod IP, (b) the sidecar container, and (c) the logs already written to emptyDir?
(a) Pod IP remains unchanged because the pause container keeps the Pod's netns alive; (b) Sidecar keeps running unaffected; (c) Logs in emptyDir are preserved because emptyDir is bound to the Pod's lifecycle on the node, not individual container restarts.
5. Troubleshooting: A new Pod is stuck in Pending in a busy cluster, and kubectl describe pod shows 0/5 nodes are available: 5 Insufficient memory. How do you triage whether this is a real capacity shortage, bad requests/limits, or scheduling constraints?
(1) Inspect the Pod's own resources.requests.memory for typos (e.g., 64Gi instead of 64Mi); (2) Run kubectl describe nodes to compare Allocatable vs. Allocated memory requests (scheduler scores based on requests, not actual runtime RSS); (3) Check for resource fragmentation across nodes where aggregate free RAM exists, but no single node has enough unreserved contiguous memory.
6. "What would happen if...": What would happen if two containers inside the same Pod both try to listen on TCP port 8080 on 0.0.0.0? And what if a container's main process ignores SIGTERM?
(1) Because both containers share the same network namespace and port space, the second container fails immediately with bind: address already in use (EADDRINUSE) and enters CrashLoopBackOff; (2) If PID 1 ignores SIGTERM, it stays running until terminationGracePeriodSeconds (default 30s) expires, then receives an uncatchable SIGKILL (kill -9).
